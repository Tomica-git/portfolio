# 半導体メモリ検査工程の業務効率化 ― Excel 関数 + VBA による自動化

> 技術派遣先での破断面観察業務において、画像ファイル名の命名規則設計と  
> Excel 関数・VBA を組み合わせた自動抽出の仕組みを構築し、  
> **手作業 3〜4 時間 → 約 45 分**へ短縮した取り組みの記録です。

---

## 背景

半導体メモリの品質管理工程のひとつに**破断面観察**があります。  
サンプルの断面をマイクロスコープで撮影し、取得した画像データを約 1,000 行ある Excel 管理台帳に記録、最終的に TIBCO Spotfire（DXP）でデータを集計・可視化するという一連のフローです。

### 従来の課題

- 撮影 → 保存 → Excel 手入力 → Spotfire 集計 のすべてが手作業
- 1,000 行超のシートから該当セルを**目視で検索**し、データを 1 件ずつ手入力
- 転記ミスが頻発し、ミス修正に **3〜4 時間**かかることがあった
- Excel の入力ミスが Spotfire の集計にも波及し、やり直しが発生

### なぜ 3〜4 時間かかっていたのか

時間がかかっていた本質的な原因は、**プロセスの設計そのものにあった**。

1,000 行超のシートに数十件分のサンプルを手入力するという作業は、構造的にミスが起きやすい。
項目数が多く、行を目視で探しながら入力するため、**「どの行に入れるべきか」の確認コストが入力そのものより大きかった**。

さらに、一度入力した後に 50〜80 件の転記ミスがないかを再度目視確認する工程が必要で、
この**入力 → 確認 → 修正 → 再確認**のループが 1〜2 時間を占めていた。

> ミスが起きるのは作業者の問題ではなく、**「間違えても気づきにくい仕組み」になっていたこと**が根本原因だった。
> この認識が、「確認しなくて済む構造を作る」という設計方針につながった。

## 解決アプローチ

### 1. ファイル命名規則の設計

マイクロスコープで画像を保存する際に、後工程で必要なデータを**略語で埋め込む**命名規則を自ら設計しました。

```
例: 84-50TE04①_X.XXum破断状態A.jpg
```

| 位置 | 内容 | 抽出例 | 意味 |
|------|------|--------|------|
| 1〜5 文字目 | ウェハ型番（略称） | `84-50` | → 正式型番 `DCH003484-50` へ変換 |
| 6〜7 文字目 | ウェハ上の取得位置 | `TE` | → Top Edge（上・外側）等 |
| 8〜9 文字目 | サンプル番号 | `04` | → 4 番目のサンプル |
| 10 文字目 | 破断方向 | （3 パターン） | → IFERROR + FIND で判定 |
| `_` 〜 `um` の間 | 測定値 | `X.XX` | → FIND + MID + ×1 で数値変換 |
| `um` 〜 `.jpg` の間 | 破断状態 | `破断状態A` | → 破断起点のフィルター用分類 |

> ポイント: ファイル名自体を**構造化データのソース**にすることで、手入力を排除する設計です。

### 2. マクロ付き Excel（破断面自動入力マクロ.xlsm）による運用フロー

VBA マクロとボタンを組み込んだ `.xlsm` ファイル（**4シート構成**）で、以下の手順で操作します。

#### シート構成

| シート名 | 役割 |
|----------|------|
| 操作 | VBA ボタン操作の起点。フォルダ選択・ファイル名取得を実行 |
| filelist | VBA が取得したファイル名を A 列に出力するバッファ |
| 貼り付け場所変換 | ファイル名を貼り付けると B〜G 列の関数が各フィールドを自動抽出。H 列に複合キー（型番 & 位置 & 番号 & 方向）を生成 |
| まとめDB | 約 1,000 行の管理台帳。A〜D 列はあらかじめ登録された識別情報。E・F 列は INDEX/MATCH で貼り付け場所変換の測定値・破断状態を自動取得 |

#### 運用手順

| 手順 | 操作 | 結果 |
|------|------|------|
| ① | 「操作」シートの**【選択するフォルダを決定】**ボタンを押す | フォルダ選択ダイアログが開く |
| ② | 画像ファイルのあるフォルダを選択 | C5 セルに選択したフォルダのパスが表示される |
| ③ | **【選択したフォルダからfilelistのシートにファイル名を張り出す】**ボタンを押す | 「filelist」シートの A 列に全ファイル名が上から下へ出力される |
| ④ | filelist の A 列を全選択 → コピー | ファイル名をクリップボードにコピー |
| ⑤ | 「貼り付け場所変換」シートの A 列に貼り付け | B〜H 列の関数が自動で各フィールドを抽出し、H 列に複合キーを生成 |
| ⑥ | 「まとめDB」シートを確認 | E・F 列の INDEX/MATCH 関数が複合キーを照合し、測定値と破断状態を正しい行へ自動転記 |

> 詳細は [`破断面自動入力マクロ.xlsm`](破断面自動入力マクロ.xlsm)（VBA + 関数設定済み）を参照してください。

### 3. Excel 関数によるファイル名パースと自動転記

取得したファイル名から、Excel 関数を使って各フィールドを自動抽出し、管理台帳へ自動転記します。

#### ウェハ型番（1〜5 文字目 → IF ネストで正式型番へ変換）

```excel
=IF(MID(A2,1,5)="80-50","DH260507580-50",
 IF(MID(A2,1,5)="84-12","CE260402384-12",
  IF(MID(A2,1,5)="84-50","DCH003484-50","該当なし")))
```

`MID` で抽出した 5 文字を `IF` のネストで略称→正式型番へ変換。  
どの条件にも一致しなければ「該当なし」を返す。  
当初は `LET + IFS` で実装したが、旧バージョンの Excel で `@` 演算子が自動挿入され `#NAME?` エラーが発生したため、**全バージョンで動作する IF ネスト**に変更した。

#### 取得位置（6〜7 文字目 → IF ネストで正式名へ変換）

```excel
=IF(MID(A2,6,2)="TE","Top Edge",
 IF(MID(A2,6,2)="BM","Bottom Middle",
  IF(MID(A2,6,2)="Ct","Center",
   IF(MID(A2,6,2)="LE","Left Edge",
    IF(MID(A2,6,2)="RE","Right Edge","該当なし")))))
```

`Edge`（外側）・`Middle`（中央）・`Center`（真ん中）と、Top / Right / Bottom / Left の 4 方向を組み合わせて取得位置を判断。

| コード | 変換結果 |
|--------|---------|
| `TE` | Top Edge（上・外側） |
| `BM` | Bottom Middle（下・中央） |
| `LE` | Left Edge（左・外側） |
| `RE` | Right Edge（右・外側） |
| `Ct` | Center（ど真ん中。範囲が狭いため 4 方向の区分なし） |

#### サンプル番号（8〜9 文字目 → *1 で数値変換）

```excel
=MID(A2, 8, 2) * 1
```

`MID` で抽出した文字列 `"04"` を `* 1` で数値 `4` に変換。Spotfire での集計時に数値型として扱えるようにする。

#### 破断方向（10 文字目）― IF + IFERROR + FIND による堅牢な判定

パターンが 3 種類に限られていたため、単純な `MID` で 1 文字抽出するのではなく、**IFERROR と FIND の組み合わせ**でエラーに強い判定式を設計しました。どのパターンにも該当しない場合は「該当なし」を返します。

```excel
=IF(IFERROR(FIND("①",A2),0)
   +IFERROR(FIND("②",A2),0)
   +IFERROR(FIND("③",A2),0)=0,
  "該当なし",
  MID(A2,
    IFERROR(FIND("①",A2),0)
   +IFERROR(FIND("②",A2),0)
   +IFERROR(FIND("③",A2),0),1))
```

> **設計意図:** `MID` で固定位置から抽出する方法では、ファイル名に想定外の文字が混入した場合にエラーが発生する。FIND でパターンの存在位置を検索し、見つからなければ 0 を返す方式にすることで、**抽出エラーを最小限に抑えた。** 合計が 0（どのパターンにも該当しない）の場合は「該当なし」を返す。

#### 測定値（`_` と `um` の間）― FIND + MID + 数値変換

```excel
=MID(A2, FIND("_", A2) + 1, FIND("um", A2) - FIND("_", A2) - 1) * 1
```

| ステップ | 処理内容 |
|---------|---------|
| `FIND("_", A2)` | `_` の位置を取得 |
| `FIND("um", A2)` | `um` の位置を取得 |
| `MID(...)` | 2 つの位置の間の文字列を抽出 |
| `* 1` | テキスト → 数値に変換（Spotfire での集計用） |

#### 破断状態（`um` 〜 `.jpg` の間）

```excel
=MID(A2, FIND("um", A2) + 2, FIND(".jpg", A2) - FIND("um", A2) - 2)
```

`um` の直後から `.jpg` の直前までの文字列を抽出。
破断起点がどこかを判別する**フィルター用の分類データ**として使用。

#### 複合キー（貼り付け場所変換 H 列 ― まとめDB との照合キー）

```excel
=B2&C2&D2&E2
```

正式型番・取得位置・サンプル番号・破断方向を結合し、まとめDB の MATCH 関数が行を特定するための一意キーを生成。

#### まとめDB の自動転記（INDEX + MATCH）

約 1,000 行ある管理台帳（まとめDB）には、正式型番・取得位置・サンプル番号・破断方向が**あらかじめ登録**されています。
貼り付け場所変換に画像ファイル名を貼り付けると、まとめDB の E・F 列が即座に更新されます。

```excel
' E列: 測定値の自動転記
=IFERROR(INDEX(貼り付け場所変換!F:F, MATCH(A2&B2&C2&D2, 貼り付け場所変換!H:H, 0)), "該当なし")

' F列: 破断状態の自動転記
=IFERROR(INDEX(貼り付け場所変換!G:G, MATCH(A2&B2&C2&D2, 貼り付け場所変換!H:H, 0)), "該当なし")
```

| ステップ | 処理内容 |
|---------|---------|
| `A2&B2&C2&D2` | まとめDB の識別情報（型番・位置・番号・方向）を結合して複合キーを作成 |
| `MATCH(..., 貼り付け場所変換!H:H, 0)` | 貼り付け場所変換の H 列（複合キー列）を完全一致で検索し、該当する行番号を取得 |
| `INDEX(貼り付け場所変換!F:F, ...)` | 取得した行番号を使って F 列（測定値）・G 列（破断状態）の値を返す |
| `IFERROR(..., "該当なし")` | ファイルが未撮影の行はエラーではなく「該当なし」と表示し、視認性を保つ |

> **ポイント:** 手入力でおこなっていた「1,000 行超の台帳から正しい行を探して値を転記する」作業を、複合キー照合で大きく減らした。データの不一致や転記ミスに気づきやすい設計にしている。

#### まとめDB シートの設計

まとめDB は、すべてのサンプルの識別情報をあらかじめ網羅した**全組み合わせマスタ**です。

```
3 型番 × 5 取得位置 × 3 破断方向 × 10 サンプル番号 = 450 行
```

| 列 | 内容 | 値の例 |
|---|---|---|
| A | 正式型番 | DH260507580-50, CE260402384-12, DCH003484-50 |
| B | 取得位置 | Top Edge, Bottom Middle, Center, Left Edge, Right Edge |
| C | No（1〜10） | 1, 2, ... 10 |
| D | 破断方向 | ①, ②, ③ |
| E | 測定値（自動取得） | INDEX/MATCH で貼り付け場所変換から転記 |
| F | 破断状態（自動取得） | INDEX/MATCH で貼り付け場所変換から転記 |

**並び順:** 型番 → 取得位置 → 破断方向 → No（1〜10）の順に整列。Spotfire へのインポート時にフィルタリングしやすい構造にしている。

**条件付き書式:** E 列または F 列が「該当なし」の行はグレー（`#BFBFBF`）で行全体を塗りつぶし。未撮影・未処理のサンプルが一目でわかり、データが入ると自動でグレーが解除される。

> **設計意図:** 従来は 1,000 行超のシートから目視で行を探して手入力していたが、まとめDB ではすべての行があらかじめ存在するため「行を探す」作業を大きく減らせる。INDEX/MATCH が複合キーで照合するので、正しい行へ転記しやすい構造になっている。

### 5. バリ測定系への拡張（カットバリ自動入力マクロ.xlsm）

破断面観察の仕組みが安定して運用できるようになった後、別ラインで実施している**ALカットバリ確認業務**にも同じ思想を展開しました。業務ごとに命名規則・シート構成・担当者が異なるため、**破断面観察版とは別ファイル（`カットバリ自動入力マクロ.xlsm`）として独立させ**、それぞれの業務単独で配布・改修できる構成にしています。基本方針(ファイル名を構造化データのソースにする / 略号を IF ネストで意味のある名前に変換する / FIND+MID+IFERROR で堅牢にパースする)は破断面観察版と共通で、抽出対象のフィールドだけが業務に合わせて差し替わっています。

#### 新しいファイル命名規則

```
例: 84-50TE04_b3.20um｜b5.10um.jpg
    │    ││  │  │ │    │ │   │
    │    ││  │  │ │    │ │   └── 最大バリ高さ(｜Xとum.jpgの間)       : 5.10
    │    ││  │  │ │    │ └────── 最大バリ形状(｜直後1文字)            : b → バリ
    │    ││  │  │ │    └──────── 区切り記号(全角縦線「｜」)
    │    ││  │  │ └──────────── 中央バリ高さ(_Xとum｜の間)            : 3.20
    │    ││  │  └────────────── 通常バリ形状(_直後1文字)              : b → バリ
    │    ││  └───────────────── サンプル番号(8〜9文字目)              : 04
    │    │└──────────────────── 面内位置(6〜7文字目)                  : TE → Top Edge
    └───────────────────────── ウェハ型番略称(1〜5文字目)             : 84-50 → DCH003484-50
```

破断面観察版との違いは、測定値が**中央バリと最大バリの2点**に増えたことと、それぞれに**形状区分(バリ/ヒゲ)が付随する**こと。区切り記号として全角縦線 `｜` を採用し、`um` と組み合わせた `um｜` を中央測定値のアンカー、`um.jpg` を最大測定値のアンカーとして使うことで、数値の切り出し位置を一意に特定しています。

#### バリ測定変換シートの 7 列構成

バリ測定用は独立した `カットバリ自動入力マクロ.xlsm` として切り出し、A 列にファイル名を貼ると B〜H 列へ自動展開される構成にしました。破断面観察版と同じ VBA 2 ステップ運用（フォルダ選択 → filelist へ出力）を踏襲しつつ、シートは「バリ測定変換」に特化しています。

| 列 | 項目 | 抽出方法 | 出力例 |
|----|------|----------|--------|
| A | ファイル名 | 入力 | `84-50TE04_b3.20um｜b5.10um.jpg` |
| B | 正式型番 | 1〜5 文字目を IF ネストで変換(破断面観察版と共通) | `DCH003484-50` |
| C | 面内位置 | 6〜7 文字目を IF ネストで変換(破断面観察版と共通) | `Top Edge` |
| D | チップNo | 8〜9 文字目を `*1` で数値化 | `4` |
| E | 通常バリ形状 | `_` の直後 1 文字を `b`→バリ / `h`→ヒゲ に変換 | `バリ` |
| F | 中央バリ高さ | `_X` と `um｜` の間の数値を `*1` で数値化 | `3.20` |
| G | 最大バリ形状 | `｜` の直後 1 文字を `b`→バリ / `h`→ヒゲ に変換 | `バリ` |
| H | 最大バリ高さ | `｜X` と `um.jpg` の間の数値を `*1` で数値化 | `5.10` |

B 列・C 列は破断面観察版（`破断面自動入力マクロ.xlsm` の `貼り付け場所変換` シート）と**完全に同じ IF ネスト式**を使っているため、ウェハ型番や面内位置の辞書を追加・変更する際は両ファイルで同じ修正を反映するだけで済みます。

#### 形状コードの変換ルール(E 列・G 列)

```excel
=IFERROR(
  IF(MID(A2,FIND("_",A2)+1,1)="h","ヒゲ",
   IF(MID(A2,FIND("_",A2)+1,1)="b","バリ","該当なし"))
 ,"該当なし")
```

- `_` の直後 1 文字を `MID + FIND` で取り出し、`b` / `h` を日本語ラベルへ変換
- G 列は同じロジックで基点を `FIND("｜",A2)+1` に差し替えただけ
- 想定外の文字が来た場合は `"該当なし"` を返し、条件付き書式でグレー塗りにして視覚的に検出

#### 数値抽出式(F 列・H 列)

```excel
' F列: 中央バリ高さ
=IFERROR(
  MID(A2, FIND("_",A2)+2, FIND("um｜",A2)-FIND("_",A2)-2) * 1
 ,"該当なし")

' H列: 最大バリ高さ
=IFERROR(
  MID(A2, FIND("｜",A2)+2, FIND("um.jpg",A2)-FIND("｜",A2)-2) * 1
 ,"該当なし")
```

破断面観察版の測定値抽出式と同じ `FIND + MID + *1` のパターンですが、アンカー文字列を `um｜` / `um.jpg` のような**複数文字の組み合わせ**にすることで、単独の `um` が 2 回現れるファイル名でも切り出し位置がずれないようにしています。

#### 設計上の学び

- **区切り記号の選定**: 当初は `|` を検討したが、ファイル名として見分けがつきにくいため全角縦線 `｜` を採用。視認性と一意性を両立できた
- **共通辞書の再利用**: 型番・面内位置の IF ネストを破断面観察版と共通化することで、**同じ命名規則マスタを 2 つの業務で共有**する構造が自然に生まれた
- **拡張性**: ファイル名末尾の `um.jpg` を固定することで、将来さらに測定点が増えた場合も同じパターン(`｜` 区切りと `um` アンカー)で水平展開できる余地を残してある

## 技術スタック

- **Excel VBA** — フォルダ選択・ファイル名一括取得の 2 ステップマクロ + ボタン自動配置
- **Excel 関数（ファイル名パース）** — `IF`（ネスト）, `MID`, `FIND`, `IFERROR` を組み合わせ、ファイル名から全フィールドを抽出
- **Excel 関数（自動転記）** — `INDEX` + `MATCH` の複合キー照合で、1,000 行超の管理台帳への手入力を排除
- **TIBCO Spotfire (DXP)** — データ集計・可視化

## GitHub連動型ポートフォリオLP

このリポジトリには、採用担当者向けに概要を短時間で伝えるための 1 ページ HTML も含めています。

| ファイル | 役割 |
|----------|------|
| `index.html` | LP本体。改善前の工程、時間がかかった理由、改善後の工程、Before / After、GitHub導線を掲載 |
| `style.css` | LPの見た目とスマホ対応 |
| `README.md` | 技術詳細・運用手順・編集方法の説明 |

### 編集方法

1. `index.html` の各セクション文言を編集する
2. 色・余白・スマホ表示は `style.css` を編集する
3. 技術詳細を増やす場合は、LPへ長く書きすぎず、この README や関連 Markdown に追記する

LPは「第一印象」、GitHubとREADMEは「裏付け」として分けています。

### ローカル確認方法

ブラウザで `index.html` を開くと表示を確認できます。

```bash
open index.html
```

### GitHub Pagesで公開する方法

1. GitHub のリポジトリ画面で `Settings` を開く
2. `Pages` を選択する
3. `Build and deployment` の `Source` を `Deploy from a branch` にする
4. `Branch` を `main`、フォルダを `/root` に設定して保存する
5. 表示された公開URLにアクセスし、LP・README・GitHubリンクを確認する

## キャリアの経緯と転職の動機

### 大学での学び → 技術派遣へ

大学時代はソフトウェアを中心に、**プログラミングや AI の分野を専攻**していました。しかし入社当時は基本情報技術者試験などの実務的な資格を持っておらず、AI もまだ現在ほど注目されていなかったため、ソフトウェア業界は人材が間に合っている状態でした。そのため技術派遣では**製造業、いわゆるハードウェアを中心に**キャリアを積むことになりました。

### 製造現場での苦戦

半導体メモリの製造会社での派遣では、正直に言えば**手作業の精度**で苦戦しました。

- マイクロスコープでの細かなサンプル操作に慣れず、**誤ってサンプルをダメにしてしまう**ことがあった
- データ入力のミスにより、**Spotfire の発表スライドを作り直す**事態が発生した
- 繊細な手作業の連続は、自分にとって得意な領域ではなかった

### 業務効率化での成功体験

一方で、こうした手作業のミスを**仕組みで解決する**取り組みにおいては、まったく違う結果が出ました。

**誰にも頼まれていないにもかかわらず**、自発的にファイル命名規則の設計と Excel 関数・VBA による自動化に取り組み、3〜4 時間の作業を 45 分に短縮。この改善を業務報告で発表したところ、**どの業務報告よりも受けが良かった**という成功体験を得ました。

### プログラマーへの転職を決意した理由

この対比が、自分の適性を明確にしてくれました。

**手を動かす繰り返し作業**では目立つミスがあった一方で、**「どうすればミスが起きない仕組みを作れるか」を考えて実装する**領域では、自発的に動き、成果を出し、高い評価を得ることができた。

大学で学んだプログラミングと AI の知識がこの現場で初めて活き、Excel 関数と VBA という限られたツールでも目に見える改善を生み出せた。ならば、**本格的なプログラミング言語を使えばもっと大きな課題を解決できる**はず。

大学での学びの土台、現場で手を動かして成果を出した実感、そして自分が本当に力を発揮できる領域が明確になったこと――この 3 つが重なったことが、ソフトウェア開発を本業にしたいという決意の原点です。

### この経験から得た技術的な学び

#### ファイル名を「データベース」として設計する発想

ファイル保存時の命名規則という**上流の小さな設計変更**が、下流のすべての工程に効きました。これはソフトウェア設計でいう**データモデリング**の考え方そのものです。

#### 「N 番目の文字を抽出する」だけでは不十分だった

破断方向の判定で、最初は `MID` で固定位置から取得する方法を試しましたが、想定外のケースでエラーを減らすために、`IFERROR + FIND` に切り替えたことで堅牢性を自主的に挙げられた経験は、**エラーハンドリング**の重要性を実務で学ぶ機会になりました。

## 図解画像の差し替え方法

LPの「なぜチップ強度を評価するのか」セクションでは、次の画像を参照しています。

```text
assets/images/chip-strength-infographic.png
```

差し替える場合は、同じファイル名のPNG画像で上書きしてください。横長のインフォグラフィックを推奨します。

- 推奨内容：ウェハ → ダイシング → チップ → ピックアップ → 基板実装 → ワイヤ接続 → 樹脂封止 → 検査
- 公開用に一般化し、実製品名・会社名・実測値・機密情報は入れない
- 画像生成用プロンプトは `docs/image_prompt_chip_strength.md` を参照
- 画像が未配置でもLP本文は読めるが、同パスに配置すれば自動表示される
